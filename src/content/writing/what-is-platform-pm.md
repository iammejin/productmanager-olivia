부모님께 이직 소식을 전했을 때, "너는 거기서 어떤 것을 기획하니?"라는 질문을 받았다. 친구들과 대화할 때도 유사한 질문이 반복된다. 서비스 PM으로 일한다고 하면 대부분 구체적으로 무엇을 기획하는지 묻곤 한다.

"플랫폼 PM은 어떤 일을 할까?"

서비스 개발 시 사용자들은 UX/UI 중심으로 학습한다. 하지만 사용성이 좋은 서비스를 만들려면 백엔드 플로우가 잘 구성되어야 한다.

## 1. 플랫폼 PM은 서버 개발자와 밀접하게 일을 한다

모든 서비스 PM이 개발자와 협업하지만, 플랫폼 PM은 화면 표시보다 "서버 부분에 대해서 기획을 하기 때문에 서버 개발자와 많은 커뮤니케이션을 한다."

홈화면 컨텐츠 기획 시 플랫폼 PM은 다음을 고려한다:
- 컨텐츠 노출 출처
- 노출 조건 (조회수, 공유수, 댓글 순 등)
- 어드민 필요 여부
- 이미지 형식
- 컨텐츠 재로딩 주기

이러한 점들을 정리하여 서버 과부하를 방지하도록 개발자와 논의한다.

플랫폼 PM은 화면설계, 정책 수립 외에도 "전반적인 시스템 아키텍쳐를 이해하는 역량이 중요하다." 모든 설계를 PM이 하는 것은 아니며, 개발자 의견을 수용하여 업무에 적용해야 한다.

## 2. API 문서를 적극적으로 활용하고 정책을 세운다

화면설계 시 API 문서를 활용하는 경우가 많지만, 플랫폼 PM은 API 문서 이해와 기획 능력이 더욱 필요하다. 수많은 API들이 어떻게 연결되는지 이해하는 것이 중요하다.

기능 구현 시 "기존의 API를 활용해도 되는지, 별도의 API를 구성해야 하는지 등에 대해서 더 서버 입장에서의 고민하며 기획을 해야 한다."

## 3. User flow나 화면설계보다는 시퀀스 다이어그램을 많이 그린다

로그인 플로우 기획을 예로 들면, 화면 기획으로는 일반 로그인 / 소셜 로그인 / 자동로그인을 구분한다.

플랫폼 PM 관점에서는 각 로그인 방식이 다른 API 구성을 가진다. 자동로그인의 경우 토큰을 이용하여 사용자 액션 없이 진행되어야 하므로, 호출 순서와 프로세스가 별도로 설계된다. 이러한 단계 기획에는 user flow나 화면설계보다 시퀀스 다이어그램이 적합하다.

---

## 서비스 PM와 플랫폼 PM의 주요 차이

1. 서버 개발자와의 커뮤니케이션 시간이 많다
2. API 문서 파악 능력과 시스템 아키텍쳐 이해가 중요하다
3. 화면설계 UI/UX보다는 시퀀스 다이어그램을 많이 그린다

일하면서 "나는 어디까지 알아야 하는 걸까?"라는 고민이 들기도 하지만, 플랫폼 PM으로서의 역량을 키운다면 더욱 탄탄한 기획력을 갖출 수 있을 것이다.
